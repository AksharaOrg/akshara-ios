# Android parity and suggestion performance review

Reviewed 2026-09-19. Fetched Android's remote; local `HEAD` and `origin/main` both point to `b00e15d` (Play build 17). The previous feature release is `28b2f08` (build 16). Android also has substantial uncommitted changes; those are listed separately below. Existing iOS changes were preserved.

The iOS changes in this task implement holding `123`, dragging onto a number or punctuation key, and releasing to insert once and return to letters. A normal tap still leaves Numbers open. Sliding onto `#+=` opens the extra symbols during the same hold. Releasing over a utility key or outside the grid inserts nothing and returns to letters. The recognizer lives on the root view so changing key layouts does not remove it. Its target uses the existing keyboard hit regions, including gaps. Additional key presses are ignored while the gesture is active.

Suggestions now debounce for 25 ms instead of 75 ms. Cancellation tokens skip obsolete queued rankings and stop subsequent correction/emoji/next-key work after a request becomes obsolete; the existing generation check still rejects stale UI results. An in-progress provider call is not interrupted. A bounded 32-request cache reuses rankings when backspacing or retyping, keyed by prefix, preceding words, and result limit. Learning and accepted suggestions invalidate the cache.

Pushed Android behavior still missing from iOS:

| Priority | Behavior | Android evidence | iOS gap / proposed work |
|---|---|---|---|
| 1 | Double-tap Shift for caps lock | `ime/ShiftLatch.kt`; `KeyboardView.updateShift` | iOS only toggles one-shot `shift`. Add an explicit caps-lock state and a rapid second-tap threshold, preserving Wijesekara shifted mappings. |
| 1 | Swipe left on Delete to preview and delete a span | `ime/TouchController.kt`, `DELETE_SWIPE`, `onCommitPreviewDelete` | iOS has repeated deletion but no swipe selection/preview flow. Prototype host-editor compatibility and Sinhala grapheme boundaries before shipping. |
| 2 | Drag between ordinary keys to change the selected key before lift | `TouchController.pointerMove` and `pointerUp` | iOS commits most letters on touch-down. General slide correction needs an intentional change to commit timing; the new `123` gesture alone does not add it. |
| 2 | Flick down for a key's first alternate | `KeyboardLayout.charDef` populates `flickOutput`; `TouchController` handles `FLICK` | iOS has long-press Wijesekara/punctuation alternatives but no flick-down path. Start with discoverable alternate hints and avoid collisions with existing gestures. |
| 2 | Persistently learned per-key touch centers | `ime/TouchPersonalizationStore.kt`, `TouchController`, `TouchDecoder.kt` | iOS already expands hit regions using predictions and covers key gaps, but does not learn touch offsets or penalize a recently corrected touch. Port the bounded local model only with accuracy tests. |
| 3 | Expand/collapse the clipboard board by dragging its handle | `KeyboardView` clipboard drag/velocity/height handling added in build 17 | iOS's clipboard panel remains constrained to the keyboard content container. Add a bounded expanded height and accessible toggle. |

Android's local, **uncommitted** additions include persistent English switching, an English prediction/next-word/correction provider and resources, and inline autofill integration. Persistent English plus local English suggestions would be useful iOS follow-ups: iOS currently offers English for one word and literal input for certain fields, but no equivalent English prediction provider. Inline autofill is Android platform integration and should not be treated as a direct iOS port. Android's new Sinhala autocorrection work is not an iOS feature gap: iOS already has a verified lexicon, correction suggestions, conservative replacement and undo protection.

Several build-16/17 features already have iOS equivalents: one-word English, emoji search and skin tones, two emoji suggestion chips, clipboard history/pinning/removal, one-handed positioning, adjustable geometry, high contrast, suggestion text morphing, predictive hit regions, and coverage of gaps between keys. Their presence alone is not a reason to port Android code. Exact visual and interaction parity would require device-side comparisons.

SQLite is worth evaluating for **cold loading**, but there is no measured evidence here that replacing the storage layer will fix all reported typing lag. The current iOS provider already binary-searches sorted words, keeps a bounded set of ranking winners, and memory-maps the bigram corpus. It still constructs indexes on startup and parses follower rows for context queries. A prebuilt SQLite database could avoid that startup index construction, or a prebuilt binary offset index could retain the existing format with less change. SQLite needs appropriate indexes for efficient searches and sorting; see [SQLite's query planner documentation](https://www.sqlite.org/queryplanner.html).

Recommended next step: measure cold-open time, key-to-rail latency (median/p95), peak extension memory and accuracy on an older iPhone, with suggestions and predictive hit areas independently enabled/disabled. Compare the current provider against a prebuilt, read-only SQLite prototype using indexed word-prefix ranges and context indexes for bigrams/trigrams. Keep learned data separate from the bundled corpus and run the same prediction fixtures against both. Do not choose SQLite solely from cached desktop timing.

Validation: the iOS app and keyboard extension build successfully for the iOS 26.5 simulator; existing UIButton deprecation warnings remain. `zsh Scripts/test_sinhala_predictions.sh` passes, including the added queued-cancellation and cache invalidation regressions. In the unoptimized desktop test run, one uncached lookup for `ක` after `එය` took 16.713 ms; 1,000 repeated cache hits averaged 0.0005 ms. These timings exclude UI, correction/emoji/next-key stages and cold model loading and are not an end-to-end speedup claim.

The hold-and-drag interaction has been compile-checked, not interactively verified. Before release, check on iPhone and iPad in all three input modes: normal `123` taps, hold then release over the original key, digits and punctuation, `#+=` symbols, gaps and outside-grid cancellation, rapid typing afterward, Shift state, keyboard dismissal, field switching and a second finger during the hold. Verify precisely one insertion and return to the original letter mode.
